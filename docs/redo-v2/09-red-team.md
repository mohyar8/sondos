## Verdict: GO-WITH-FIXES

This is an unusually rigorous Run 1 for a fleet of five agents working in parallel on the same day. I spot-checked eight load-bearing factual claims against the actual code (migrations 0001 vs 0002 byte-identity, `wrangler.jsonc`'s missing R2/cron bindings, `worker/index.ts`'s `fetch`-only export, the hardcoded 24h hold at `admin-workflow.ts:17`, `.gitignore`'s missing `.dev.vars`/`.wrangler/` entries, `shared/booking.ts`'s nullable `photoCount`, `src/api/admin.ts`'s limit≤100/default-50 cap, and `App.tsx`'s five-literal `AppPath` type) — every one was accurate. The architecture (reuse existing statuses + additive child tables + a `flow_version` kill switch that leaves every legacy row untouched, derived-not-stored journey stages, Worker-only-reachable private R2, HMAC-signed media URLs, additive-only DDL) is sound and its rejected alternatives (Durable Objects, presigned S3 URLs, blob-URL image serving, storing stages as new statuses) are rejected for real, specific reasons, not hand-waved. That said, "well-engineered" and "safe to build as-is" are different questions. Below is the attack.

---

### 1. Load-bearing assumptions

1. **"The single owner will personally act, within SLA, across ~6 concurrent deadline types (admin SLA, hold, receipt review, selection deadline, handover slot, cron heartbeat) forever."** Evidence this is assumed everywhere: the entire timing model (`01-product-spec.md §6`), the admin daily queue (`03-design-system.md §4.14`, `ADM-01`), and the cron job table (`05-adr-architecture.md §2.2`) all depend on it; nothing enforces it. If false: the site's central selling point — "maximise customer engagement" via visible timers — inverts into visible proof the studio is behind, which is worse than the current WhatsApp-only flow because a stalled countdown is a public failure signal a slow WhatsApp reply never was.
2. **"PDPL permits transferring Saudi residents' financial receipts and private wedding photos to Cloudflare R2/D1, Firebase Auth (US), and Resend (US) — none in-Kingdom."** `05-adr-architecture.md §2.7` states this outright and gates the bucket/Runs 4/6 on the answer. If false, Runs 4 and 6 — the largest, riskiest, most novel two-thirds of the whole build — need a different storage/auth stack.
3. **"A solo photographer/non-developer owner can correctly resolve 19+ open items (D4 deposit+bank details, U1 PDPL, U6 terms text, U9 retention, U13 delivery fee, U15 MFA, U17 ZATCA…) without professional help, on a timeline that doesn't stall the build."** Several of these are explicitly legal/accounting questions (`01-product-spec.md §12.5`, `05-adr-architecture.md §4.4`). If false, the build stalls repeatedly waiting on answers, or an agent-proposed default (20% deposit, a plain-language "terms" summary) quietly becomes real policy without real legal review.
4. **"The production D1 database's unknown state (D8) can be safely repaired."** `00-inspection-report.md §11` and my own read of `app/migrations/0001_initial.sql` and `0002_create_booking_schema.sql` confirm the files are byte-identical `CREATE TABLE` statements — a fresh `migrations apply` fails at 0002. D8 in `decisions.md` is marked `UNKNOWN`. If the remote database's real history diverges further from what a local read-only inspection shows (manual hotfixes, partially-applied migrations), the "repair" step risks the one datastore holding every real booking and every SAR of revenue history.
5. **"Nobody needs to know how many hours/weeks this actually takes to build before agreeing to it."** No artifact gives a build-time estimate; the ADR prices hosting in SAR/month in detail (`§5`) but never prices engineering time. For a "budget-conscious solo founder" (per this review's own brief), the unknown is the labor, not the SAR 19-120/month hosting bill.

### 2. Pre-mortem — three most likely 3-months-later failure stories

**Story A — "Launched, but the admin drowned."** Receipt review, gallery review-before-publish (potentially hundreds of photos/event, `03-design-system.md §4.12`), and selection follow-ups pile up faster than one person shooting/editing weddings can clear them. *Earliest warning sign:* the admin queue's "إيصالات بانتظار المراجعة" / "متأخرة" counts (`03-design-system.md §4.14`, `08-copy-ar.md §9.5`) trend upward week over week instead of toward zero.

**Story B — "PDPL answer arrives after the fact."** Under time pressure, someone creates the R2 bucket and flips `ONLINE_CONFIRMATION="on"` before U1 has a written answer, because nothing technical stops them (Fatal Flaw #2 above). Three months later a compliance review or a customer data-subject request surfaces that receipts/photos have been sitting outside the Kingdom the whole time. *Earliest warning sign:* an R2 bucket or `ONLINE_CONFIRMATION="on"` appears in the Cloudflare dashboard/`wrangler.jsonc` before a dated file exists answering U1.

**Story C — "The stepper freezes and nobody notices."** Run 2/3 is built by an engineer reading `01-product-spec.md`/`03-design-system.md` (the documents literally named "spec" and "design system") without fully internalizing the ADR's overrides. The 8-step stepper ships as specified, terminating at "الاستلام"; brides who've received their album see no further progress even though copy-ar.md already promises a stage-15 privacy-cleanup message. *Earliest warning sign:* `W8-4`'s "walk all 15 stages at runtime" QA pass either catches this (if it cross-checks the stepper against all 15 stage ids) or ships it, in which case the first sign is silence in the post-handover funnel — no engagement, no complaints, just brides who stop checking a page that stopped updating.

### 3. Attack the numbers

- **Hosting costs (SAR 18.75 → 120.30 → 1,212.30/month)** are the one well-sourced figure set in this bundle: explicit vendor tiers, explicit formulas, a stated business ceiling (~31 bookings/month from the existing one-booking-per-date unique index) that correctly caps the "1,000 bookings/month" column as a stress test, not a forecast (`05-adr-architecture.md §5`). No objection here — this is the opposite of "feels right."
- **The 20% deposit default, 30-photo coverage-only default, 48h hold, 14-day selection window, 30-day retention** are all consistently labeled "proposed default" and traced to a single source (D4/D5 in `decisions.md`) everywhere they're repeated (`01-product-spec.md §12`, `03-design-system.md §9`, `07-api-contracts.md §7`, `08-copy-ar.md §12`) — good citation discipline, not invented facts. But D5 in `decisions.md` is still marked **PROPOSED**, not **DECIDED (owner delegated)** the way D1/D2 are. Nobody has actually asked the owner to bless these numbers the same way D1/D2 were blessed; they risk becoming policy by default inertia the moment Run 3 hardcodes them into `shared/timing.ts`.
- **The one number that's simply missing: engineering hours.** 12 new tables, 33 new/changed endpoints, 2 dedicated security-audit workstreams, 6 new admin sections, and 8 sequential runs have zero time estimate anywhere. "Attack the numbers" normally means halving an optimistic estimate — here there is no estimate to halve. That is a bigger gap than an optimistic one.

### 4. Attack the downside — worst realistic case, riyals and hours

- **Direct/survivable:** hosting cost is bounded and small (SAR ~19-120/month at realistic volume) and every new-flow feature sits behind `flow_version`/`ONLINE_CONFIRMATION` kill switches that leave the *existing, revenue-bearing* booking flow completely untouched throughout (`05-adr-architecture.md §2.1`: legacy rows "drain naturally," "get no online panel," "never expired by cron"). This is a genuinely good property: the current business is never put at risk by this build, even if it stalls halfway. Worth crediting explicitly.
- **Real exposure:** unbounded engineering time/cost sunk into Runs 3-4 (infra + receipts) while stuck waiting on D4/U1/U6/U15 answers only a lawyer/accountant/the owner can give — money and hours spent with `ONLINE_CONFIRMATION` still stuck "off." Survivable but wasteful; the fix is sequencing (see steel-man below), not abandoning the plan.
- **Worst-case, not quantifiable in SAR here (and I won't invent a fine figure the artifacts don't supply):** a privacy incident — a leaked receipt or a bride's private photo set exposed via a compromised single-factor admin account, or data stored abroad before a PDPL answer existed — hits a brand whose *entire* public differentiation is "جميع الصور تُنشر بموافقة العروس." For a single-person brand this is not a line-item cost, it's existential-to-the-brand reputational risk. This is exactly why Fatal Flaws #1 and #2 above matter more than any feature in the spec.

### 5. Steel-man the alternative

The current site is defective (`00-inspection-report.md §11-12` lists 17 defects) but *functional* for its actual job: capture a request, let the owner approve it, do everything else over WhatsApp — a channel she and every bride already use daily, with zero new PDPL exposure and zero new attack surface. Nothing in `decisions.md` documents a *measured* pain point (lost bookings, hours lost to WhatsApp chaos) — the brief is an ambition ("make it as perfect as it can be") plus a wishlist. The strongest alternative: ship **only** Run 2 (visual redesign + the owner's real photos — no new data categories, no new compliance exposure) plus the narrow bug-fix slice of Run 3 that fixes a real, already-broken defect (holds blocking a date forever, `00-inspection-report.md §12.4`/`BK-03/04`) — then **pause** before Run 4 (receipts/R2/PDPL) until the owner has real professional answers to D4/U1/U6/U15, and ideally until one real event cycle shows brides actually want a self-service portal rather than the WhatsApp flow they may already prefer. This isn't a rejection of the plan — `01-product-spec.md §1` already half-endorses this ("treat as its own change order") — it's a recommendation to make that sequencing explicit and binding rather than aspirational.

### 6. PDPL questions raised myself (compliance review failed — per harness instructions)

The ADR's own compliance section (`05-adr-architecture.md §2.7`, §4.4) is unusually thorough — residency/transfer, sensitive-data classification, retention vs. financial-record-keeping tension, DSR handling, DPAs — and I checked its residency/vendor claims (D1 has no ME region, R2 has no KSA jurisdiction option, Firebase/Resend store in the US) against no counter-evidence in the codebase; they stand unchallenged. Two questions I did not find raised anywhere and am adding, as instructed:

1. **Minors in event photography.** Weddings routinely include children (flower girls, young relatives). Processing children's images is a heightened-sensitivity category in most privacy frameworks; nothing in the ADR's compliance list (`§2.7`, six numbered questions) or the retention table (`§2.3`) distinguishes a minor's image from an adult's.
2. **Data-subject requests from non-account-holding guests.** The private post-event gallery necessarily contains unblurred images of wedding guests (family, attendees) who have no login and no account — unlike the bride, they have no self-service path, and the ADR's DSR answer ("the admin runs a procedure," `§2.7` point 5) is framed around the bride/customer relationship, not a guest who later asks to be removed from someone else's private gallery.

### Single assumption most worth testing cheaply first

**Assumption 2 (PDPL/data residency, U1).** It is the cheapest thing on this list to test — one question to a lawyer or a direct read of SDAIA's cross-border transfer rules, or even just asking the owner "are you comfortable with bride receipts and photos stored outside Saudi Arabia by Cloudflare/Firebase/Resend?" — and it is the one answer that, if "no," invalidates the single largest, riskiest, and most novel two-thirds of this entire plan (Runs 4 and 6) before a single hour is spent building them. Test this before writing any Run 3 infrastructure code; Run 2's visual redesign is independent and safe to proceed regardless, since it touches no new personal-data storage.

### Fatal flaws

**1. The Run 4/6 go-live gates (05-adr-architecture.md §4.5) are sufficient to keep real bride data safe once the portal switches on.**
- Evidence: ADR §4.5 lists, as Run-4 gates: U1 answered + bucket created, security review W4-5 passed, D4 supplied, terms text supplied. Admin-account MFA is a SEPARATE item, U15 (§7.15), addressed only to a 'security-auditor' with proposed default 'enable TOTP MFA' — it is not on the Run 4 or Run 6 go-live checklist. Yet ADR §2.0 'Single points of failure' item 7 says plainly: 'The single admin account. Whoever controls it can read every receipt and photo.' There is one admin, one password gate (Firebase email/password, no MFA evidenced anywhere in 00-inspection-report.md), guarding every bride's financial receipt and private post-event photos once Runs 4/6 ship. This is exactly the worst-case failure mode the task brief names ('a bride's private photos or a receipt leaking is the worst possible outcome for this brand'), and the checklist that is supposed to prevent premature exposure omits the single highest-impact control.
- Fix: Add 'TOTP MFA (or Firebase Identity Platform equivalent) enabled on the sole admin account' as an explicit, checked precondition in ADR §4.5 for both Run 4 and Run 6 go-live — promote U15 from an unresolved footnote to a hard gate, same tier as U1 and the security reviews.

**2. The U1 (PDPL residency) gate and the ONLINE_CONFIRMATION kill switch will reliably stop private data from going live before the residency question is answered.**
- Evidence: 05-adr-architecture.md §2.7 states 'Until it is answered, the R2 bucket is not created and Runs 4 and 6 do not go live' and §2.1 describes ONLINE_CONFIRMATION as a var-controlled kill switch — but both are process conventions written in prose, not technical controls. wrangler.jsonc (verified by direct read) today has no bucket, no crons, and nothing resembling a boot-time compliance check; nothing in any artifact describes the Worker refusing to serve /api/*/receipt or /api/*/gallery* routes if a PDPL sign-off record is missing. A rushed engineer (or the owner herself, eager to launch) can create the bucket and flip the var without that written answer existing anywhere.
- Fix: Make the gate self-enforcing: require a checked-in, dated file (e.g. runs/redo-v2/compliance/pdpl-decision.md) whose absence a deploy script or a Worker boot-time assertion treats as fatal for the media/receipt/gallery route registrations — so 'the gate' is code, not memory.

**3. The always-visible journey stepper (03-design-system.md §4.8) correctly represents a booking's progress from request to privacy clean-up.**
- Evidence: Design-system §4.8 builds an 8-step horizontal stepper 1) الطلب … 8) الاستلام, explicitly mapped 1:1 to decisions.md's original 8-item proposed journey. But the ADR (§2.1), the API contract's BookingStage enum (07-api-contracts.md §3.A / §8 schema), and the copy deck (08-copy-ar.md §4.1, a 15-row table) all define 15 derived backend stages as the actual source of truth — including two stages AFTER handover, `completed_feedback` and `privacy_cleanup`, for which copy-ar.md §4.2 rows 14-15 already writes specific guidance text ('لأسباب تتعلق بالخصوصية، تُحذف معاينات معرض صوركِ تلقائيًا…'). The 8-step stepper has no step 9 or beyond — it terminates at 'الاستلام'. No artifact reconciles the two models; copy-ar.md's own §4 preamble flags a different conflict (the /gallery route) but is silent on this one.
- Fix: Before any Run 2/3 engineer builds the stepper component, produce one explicit stepper-position → 15-stage-id mapping (e.g., add a 9th collapsed 'ما بعد التسليم' position covering stages 14-15, or redesign the stepper to keep advancing after handover) and update 03-design-system.md §4.8 accordingly.
